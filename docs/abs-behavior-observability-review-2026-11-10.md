# ABS MVP：从数值账本到可验证的自主行为

日期：2026-11-10，Asia/Shanghai。范围：当前源码 + 本机运行接口只读抽样。未修改运行配置、未唤醒大肥鱼、未发消息、未操作浏览器或发布内容，未读取私人对话正文。本报告是设计研究，不是已实施功能。

## 1. 结论

用户感受到的落差，不能简单归结为“行动太少”。当前实现完成了 **状态变化 → 内心独白投递**，并对部分工具结果回填数值；但没有形成可观察的 **自主选择 → 实际尝试 → 外部结果 → 记住收获 → 后续延续 → 用户感知** 链路。

建议保留“ABS 只提供状态，大肥鱼自己决定”的边界，不退回系统替鱼选择任务。下一步优先级是：

1. 先能看清每次唤醒之后发生了什么，包括未知、失败与真正的暂不行动。
2. 补齐浏览器、网页读取、主动联系和主人跨渠道回复的证据。
3. 给鱼保留自己感兴趣的问题和未完成活动，减少每次醒来从零开始。
4. 把后台探索与打扰主人分开控制，再独立试验唤醒频率。
5. 用完整行为片段和用户体验评价验证，而不是用满足度或工具调用数当成功指标。

### 2.3 “没有逛贴吧”现在不能直接成立

运行技能目录确有 `browser-cdp`、`homepage-operations`、`tieba-browsing`。

但同一个贴吧技能内部已有状态不同步：

- 目录简介仍称“资料学习版，浏览器实操待验证”。
- revision 4 指南称 11-09 已完成吧列表、普通帖及回复阅读、吧内搜索；仍写发布未实测。
- 最新经验又记述 11-09 经主人明确授权发布过回复并刷新核验。

**这些是技能库中的历史记述和证据线索，不是本次独立复验的网页结果，也不足以证明 ABS 自主发起了活动。** 经验中部分引用仅写“本会话”，缺少可机器定位的 session/turn/event 引用。

因此至少存在三种不同问题：实际是否访问、是否自主发起、是否被用户感知。当前账本不能区分。技能“方法指南、能力验收状态、最近活动事实”也应分离，避免旧简介掩盖新进展。

## 3. 源码确认的问题

### 3.1 数值不是行为决策模型

[ABS README](<../core/modules/abs/README.md#L1-L28>) 明确：当前是 self-review slice，ABS 不再生成动机、评分候选或派任务。[service](<../core/modules/abs/service.js#L40-L52>) 会归档并清空旧动机/执行列表。

因此满足度变化符合公式，只能证明状态层运行，不能证明模型理解、采用或据此行动。当前没有训练或奖励优化过程；这里的“加分”是状态回填，不是模型学会了某种行为。

### 3.2 内心独白有愿望，但没有持久的兴趣对象

[review](<../core/modules/abs/review.js#L25-L39>) 按五档缺口输出固定文案；[渲染末尾](<../core/modules/abs/review.js#L79-L91>) 以“最近有没有什么让我在意……”提问，再以“不急着非做点什么……发会儿呆”结束。

源码可确认：模板不带兴趣主题、上次活动未解决的问题或待续内容。合理但未验证的假设是：反复泛化的愿望加上允许不行动，容易产生口头回应而不是具体探索。不能因此取消“不行动”的权利；应试验增加具体、真实且由鱼自己维护的关注点。

### 3.3 观察器覆盖的是工具子集，不是生活经历

[host](<../core/modules/abs/host.js#L110-L175>) 只观察 `web_search/read/read_image/write/edit/bash`：

- 不覆盖 `web_fetch`、`social_send_owner_message`、日记或技能工具结果。
- bash 无语义验证器，浏览器自动化即使成功，通常也仅是 `unverified_activity`。
- web_search 有 URL 元数据就算取得内容，不等于打开原文、理解或有新发现。
- 搜索与本地活动都进入 curiosity；[service](<../core/modules/abs/service.js#L173-L200>) 使用同一个 explorationGain。
- 捕获了 session/seq，部分有 turn，但没有保存统一 trigger→review→turn→activity 的关联；搜索观察甚至未携带 turn 字段。
- 普通主人请求中的读文件也能提高探索满足度。不能把这些变化一概称为“自主探索”。

必须区分“工具成功”“活动完成”“事实可信”“用户觉得有意思”，不再用一个 success 包办。

### 3.4 跨渠道社交反馈不闭合

[host](<../core/modules/abs/host.js#L118-L122>) 排除所有 `isChannelUserMessage`；[社交来源识别](<../core/modules/social/policy.js#L7-L8>) 包括钉钉进入的渠道消息。这意味着已绑定主人在钉钉回复，也不会通过这条观察路径增加社交满足度。

修复不能简单接受所有外部消息：应使用 Host 验证过的主人绑定身份，只接纳真实主人消息、排除机器人回声，并按平台 messageId 去重。陌生人、群聊和模型自述不可伪装成主人互动。

另有能力文案不一致：[persona](<../core/modules/social/persona.js#L5-L7>) 允许主动分享近况/聊两句，而[发送工具](<../core/modules/social/tools.js#L9-L12>) 写“只在确实需要主动提醒或告知”时用。可能抑制轻量主动聊天，影响需实际对照验证。调整应统一允许范围与打扰边界，而不是强迫每轮发送。

### 3.5 调度节奏和状态动力学混在倍率里

[调度](<../core/modules/abs/service.js#L119-L154>) 以 ABS 时间计算审查，受倍率和现实时间约束；失败后同样计算下一轮，agent-busy 没有专用短重试路径（[wake](<../core/modules/abs/service.js#L238-L274>)）。

1× 参数下，单次探索 +0.15 相当于 `0.15 / 0.004 = 37.5` 小时自然衰减；单条主人消息 +0.05 相当于 `0.05 / 0.008 = 6.25` 小时。仅是未截断时的数值等价，不表示系统必然休眠这么久。

这说明一次本地阅读也可能显著稀释探索缺口，但尚不能证明它是当前行动少的主因。倍率同时改变衰减与唤醒节奏，会混淆“更想行动”和“有更多机会行动”。后续应独立配置这两者。

### 3.6 UI 展示的不是行为闭环

当前[页面组合](<../core/modules/abs/lab.js#L320-L329>) 主要是主人状态、鱼的满足度、时间设置与事件抽取。旧审计/变化账本组件仍在源码，但不在这一页面组合内。

[事件面板](<../core/modules/abs/events-panel.js#L61-L85>) 展示最新 30 条对话抽取，正确标注“自述/意图不代表执行”，但它并不是行动证据库。只把它改成更漂亮的时间线，仍回答不了“为什么这轮没行动、探索收获是什么”。

### 3.7 次级工程风险

- [host](<../core/modules/abs/host.js#L92-L101>) 对 flush 未确认返回 `accepted:true,status:reconcile`，而 [service](<../core/modules/abs/service.js#L254-L266>) 仅按 accepted 记 ReviewDelivered。当前导出样本没有这种 reconcile，属于口径风险，不是已经确认的本次故障。
- 现实最小间隔主要通过 nextWakeAt 实现；manual 绕过 NOT_DUE（[gate](<../core/modules/abs/service.js#L132-L137>)），不宜视为不可绕过的对外联系硬限流。
- [存储](<../core/modules/abs/store.js#L6-L7>) 只有最近 2000 条 / 8MiB 审计，观察与账本各约 200 条。仅按条数截断，活跃时覆盖时长更短，长期统计会失真。

## 4. 新的观察单位：一个行为片段，而不是一条工具日志

推荐用 `episode` 表示一件有边界的事，例如“继续了解某个帖子中的问题”。一次片段可包含多个工具，跨多轮时通过同一兴趣线索关联。不能把十次点击算十次自主行为。

```text
机会出现 → 审查/事件被接纳 → 模型轮次开始
        → 决定尝试 / 明确暂缓 / 尚无可确认选择
        → 工具或外部动作 → 已验证结果 / 失败 / 未知
        → 留下收获或待续线索 → 可选分享 → 主人回应
```

### 最小关联模型

- `episodeId, parentEpisodeId, threadId`：行为片段与持续兴趣。
- `triggerKind, triggerRef, intentOrigin`：ABS、主人请求、外部消息、定时任务、恢复等；分别记录“本轮由什么唤醒”和“原始目标来自谁”。
- `reviewId, messageId, sessionId, turnId, callId, operationId`：按宿主事实连接，不靠时间邻近猜测。
- `stateBefore, configHash, promptVersion, modelId, capabilitySnapshot`：这次机会发生的条件。
- `decisionSummary, chosenActivity, deferReason`：可选的一句话意图/选择声明；明确标注模型自报，不采集或假装还原隐藏思维链。
- `attempts[], outcomeStatus, evidenceRefs[], resultSummary, artifactRef`：客观尝试与结果。
- `contactStatus, ownerResponseRef, continuationRef, userLabel`：触达、真实回复、后续延续、体验标注。
- `startedAt, finishedAt, latency, usage, coverageStatus`：成本、延迟、是否存在观察缺口。

触发是 ABS 不代表目标一定自主：可能是在完成主人此前布置的工作。目标来源未知就标未知。一个轮次混入多个输入或重启后关联丢失，应保留多个来源/unknown，不能自动归因给最近一次 review。

### 状态口径

- `queued/accepted/started/completed` 分开；投递接纳不是完成。
- 行动结果至少 `verified/failed/unknown`；对外发送 `accepted` 不代表主人看见。
- “明确暂缓”与“轮次结束但无已观测行动”分开；更不能把缺日志当主动安静。
- 浏览器证据应包含实际目标域名/URL、页面读取或操作回执、时间和源事件引用；shell exit 0 不足。
- 发布操作的模糊结果保留 unknown，禁止通过重复发送来强行补验。
- 同一内容/同一发布操作按稳定标识去重；默认只保存必要摘要、哈希和引用，不复制账户凭证与无关网页/聊天正文。

## 5. 量化：先回答六个诊断问题

不要先造一个“生命感 87 分”。以下指标分别展示，且都附样本量、可观测覆盖率、配置分段与未知数量。

| 要回答的问题 | 指标与口径 | 如何解释 |
|---|---|---|
| 有没有获得自主活动机会？ | 有效观察在线小时、休息/忙碌/离线时长、到期机会数、接纳与实际启动数 | 将基础设施问题与模型不行动区分 |
| 获得机会后有没有尝试？ | 有真实行动尝试的 ABS 轮次 / 已完成且观测完整的 ABS 轮次；另列明确暂缓、仅文本、未知 | 暂缓并非失败；该比率不能单独最大化 |
| 真正做成了多少件事？ | 有可验证结果的自主 episode / 有尝试的自主 episode；以及每有效运行小时的自主 episode 数 | 不逐工具累加，不把用户任务算自主 |
| 有没有真的向外探索？ | 经证据确认的外部阅读片段数、独立内容数、来源分布；与本地阅读/创作分栏 | 搜索命中、打开原文、获得收获是不同阶段 |
| 有没有形成自己的连续兴趣？ | 到了复访观察窗口的 thread 中，后续另一轮实际继续推进的比例；未到期样本不算失败 | 防止每次都“想看看新东西”又从头开始 |
| 对主人是惊喜还是打扰？ | 主动触达尝试/平台接纳/真实回复各自计数；用户可选标注“有意思/一般/重复/打扰” | 未回复不等于不喜欢，未知已读不伪造已读 |

辅助指标：高缺口分档下的行动类型分布、首次行动延迟、重复内容率、每完整片段 token/时间成本、未知结果比例。

“说了想做 → 后续实际做”的承诺兑现率可以辅助，但需要区分明确承诺与随口愿望；分母应为到期且可检验的承诺，不能让模型少表达愿望来刷指标。

**需求是否影响选择**必须通过控制试验验证。高好奇缺口时搜索较多只能说明相关；同时变化的上下文、倍率、能力可用性与主人请求都可能造成混淆。

## 6. 试验台改造：先看结论，再展开证据

### 第一层：今日发生了什么

顶部直接回答：

> 今天有多少个有效机会？做成几件自主活动？其中几件向外探索？主动找主人几次？有几条兴趣继续推进？还有多少结果未知？

显示有效观察时长、数据缺口与配置变化，不把自然衰减铺成首页流水。

### 第二层：机会到结果的漏斗

`到期 → 接纳 → 启动 → 完成轮次 → 尝试活动 → 获得结果`，在每层显示具体未前进原因：忙、休息、不可用、明确暂缓、只有文本、执行失败、观察缺失。分支不是全都必须转化，安静可以是合理结果。

### 第三层：行为故事卡与兴趣线

示意，非真实本次记录：

> **继续看昨天留下的贴吧问题**  
> 来源：ABS 唤醒；目标来源：鱼自行提出。  
> 选择摘要：想确认评论中的一个说法。  
> 实际动作：读取两个公开帖子。  
> 结果：取得可追溯正文，发现一处意见分歧。  
> 留下：一个来源引用和待续问题。  
> 联系主人：本次未发送。  
> 展开：工具回执、配置、状态前后变化。

再提供“还在惦记的事”：兴趣主题、上次推进、已有证据、下一次可能复访条件、已放弃及原因。全部来自真实记录，不由 UI 编造心理故事。

### 第四层：调试抽屉

原始事件、抽取事件、满足度账本、工具日志保留，供证据核查；不再承担首页解释行为的责任。

## 7. 优化路线：保留自主权，补闭环

### P0：观测先行

1. 将 review/message/turn/tool/outcome 贯通，所有已接纳审查最终可查到轮次状态或明确 unknown。
2. 对浏览器/网页/社交结果新增证据适配，不解析任意 bash 文本来猜成功。
3. 补已绑定主人钉钉回复的去重反馈；修正跨渠道身份口径。
4. 将外部探索、本地学习、创作、用户任务分开统计，先不急着新增更多驱动数值。
5. 记录覆盖区间与版本，按可查询时间窗保留 episode 元数据；日志截断必须显式显示。
6. 做最小“今日概览 + 漏斗 + 故事卡”。先用真实已知/未知状态，不等大而全遥测平台。

### P1：让行动有对象与连续性

1. 增加由鱼自己维护的轻量兴趣线索：问题、来源、上次收获、待续点、可放弃条件。不是 ABS 派发任务队列。
2. 内部上下文按需带入少量相关线索与能力可用状态；模型仍可选择行动、换方向或安静。
3. 技能的目录介绍、方法版本、验收范围和最近活动证据分开维护，避免“已做过但目录仍写未实测”。
4. 统一主动聊天能力文案，并设置独立的联系预算、安静时段与重复内容抑制；不因提高后台活动机会就增加主人通知。
5. 给浏览器只读活动与发帖/关注等账号修改设不同边界。已授权过一次发帖，不自动变成长期发布授权。

### P2：再调节律与反馈

1. 将“状态变化速率”和“获得思考机会的节奏”拆开。
2. 只对确定尚未投递的忙碌失败做有限延期/idle 后重试；接纳不明、发送结果未知不能盲目重试。
3. 试验 120 分钟与 60 分钟机会间隔，保持倍率、人格、模型、联系上限不变；不要直接用 60× 提速代替行为实验。
4. 反馈按完整活动与新证据去重、限制重复资料收益；是否分拆探索/创作需求，等分类数据说明有必要再做。
5. 主会话的普通 followup 通常产生可见回复；若想真正提高后台探索而不刷屏，需要独立的内部执行/静默输出能力。此为架构变更，不是藏掉一条气泡即可完成，也不必变成另一个人格。

## 8. 小规模验证计划

所有会改变运行行为的试验都需另行确认；本轮未启用。

1. **基线阶段**：先上线 P0，固定 1×、模型和 prompt，采集 3–7 个可比活动日。时间只是建议，需同时报告实际有效机会和完整片段数，低样本时延长。
2. **连续性试验**：保持唤醒频率不变，只增加由鱼维护的兴趣线索。比较外部有效片段、后续复访、重复空泛回复及体验标注。
3. **频率试验**：保留相同兴趣机制与联系上限，只比较 120/60 分钟；看有效产出是否增加，还是只增加 token 和泛泛回复。
4. **状态贡献试验**：先在隔离、无外发副作用的固定上下文集里比较状态文本与中性唤醒；再考虑受控线上分时试验。shadow 不调用模型，不是同机会的行为对照。
5. 可用 A/B/A 或分块随机窗口减少日期差异，但一个有记忆的 agent 存在跨窗口延续效应，要记录 thread 历史，不能伪装独立样本。每组约 30 个完整机会也只够探索性判断，不承诺统计显著。

优先选择能增加**可验证、自主、有连续性且对用户有意义的活动**的方案，同时不增加打扰、重复发布或未知外部效果。用户每天可选一次轻量反馈，比要求逐条给所有日志打分更合适。

## 9. 建议下一步交付

最值得先实施的切片不是“让鱼每隔几分钟去贴吧”，而是：

> **一次唤醒一条可追踪行为链 + 浏览器/社交结果证据 + 今日行为概览。**

它完成后，可以明确判断瓶颈发生在机会、选择、执行、收获、延续还是展示。当前原型已经证明数值与唤醒链路能运转；下一轮应证明的，是大肥鱼能否在无需主人逐步指挥的情况下，形成有证据、有后续、偶尔值得分享的经历。

# 大肥鱼连续语音聊天 · 三端架构设计 v1

设计稿，2026-11-13。首个验证端为 DSH 聊天面板。

## 用户体验

用户点击一次「开始语音聊天」，应用打开麦克风并持续监听。用户说完一个轮次后，应用自动转写并发送一条聊天消息。发送后麦克风继续监听，用户可以接着说。点击「结束语音聊天」结束本轮会话。

例如，用户说“帮我记一下”，短暂停顿后接着说“明天下午三点开会”。如果两段属于同一轮，应用将它们合成一条消息自动发送。随后用户再说“再提前十分钟提醒我”，应用自动发送第二条消息。

## 收音、判定轮次与发送

1. 用户开启语音聊天时绑定当前聊天与本次语音会话，检查权限和识别器状态。采音实际开始后显示「正在聆听」。
2. 适配器检测人声并持续采音。短停顿可供识别器分段，同一轮的分段按顺序合并。用户在轮次结束前继续说话时，重新开始计算静音时间。轮次结束阈值在目标设备上用自然停顿样本校准。
3. 持续静音达到轮次结束条件，且该轮所有分段都已返回最终文本后，按聊天消息提交。静音、空白结果不产生消息。每轮带唯一标识，同一轮只提交一次。
4. 收音与识别、发送独立运行。上一轮正在转写或助手正在回复时，继续接收下一轮。按说话顺序投递；宿主忙时在当前语音会话中暂存，待宿主可接收时再送。队列接近上限时提示用户，达到上限时暂停收音并保留已接收轮次。
5. 用户点击结束时立即释放麦克风。建议将已经说出口的尾句显示为「正在处理最后一句」，转写完成后自动发送。切换聊天或卸载时取消待处理轮次，禁止旧结果写入新聊天。

语音消息使用独立的待发送文本。聊天输入框仍归键盘输入所有，自动发送不会清空或夹带用户正在编辑的草稿。首次设计按文字回复验收；助手是否朗读回复、朗读期间能否打断是独立于自动发送的产品决定。如加入朗读，需验证扬声器回声不会触发下一轮。

## 三端实现边界

| 运行端 | 采音与识别 | 首轮验证 |
| --- | --- | --- |
| DSH 插件 | 面板采音，用 VAD 检测人声并分段。通过已认证的 Remote 调用宿主 SenseVoice，按宿主公布的音频限制提交 PCM16 WAV | 用 catalog、follow 确认识别器就绪，用 transcribe 验证回包；检查真实聊天忙闲切换时能否按序发送 |
| 独立 macOS | 由原生适配器管理麦克风及 Apple Speech 任务，检查中文语言、权限和本机识别能力 | 连续多个识别任务之间无漏音，系统的分段结果可以合并为同一聊天轮次 |
| 独立 Windows | 由桌面应用管理采音，候选为 Silero VAD 和 sherpa-onnx + SenseVoice 本机推理 | 验证首次模型准备、普通 CPU 上的延迟、设备断开及队列积压 |

DSH 在 macOS 和 Windows 上均由插件入口选择宿主识别器。独立桌面应用各自封装采音与识别，会话层统一管理轮次归属、文本顺序与自动发送。音频和待提交文本在会话内存中暂存。

## DSH 接入约束

DSH 的转写接口返回文本，聊天投递需另走真实会话入口。当前面板的表单发送函数在忙时直接返回，且会清空输入框。接入时应复用底层会话提交能力，让语音发送得到明确的成功、忙碌或失败结果。若提交回执丢失，应先核对会话记录或利用宿主幂等能力确认投递状态。状态未知时提示用户核对，避免自动重试产生重复消息。[面板发送实现](../app/dsh/ui/runtime.js) · [DSH 语音接口](https://github.com/deepseek-ai/deepseek-harness/blob/main/docs/subsystems/voice-input.zh.md)

## 验收

- 打开聊天页时麦克风空闲。点击开始后连续说两轮，聊天记录按顺序出现两条真实用户消息，各触发一次助手响应，全程无需再点击。
- 句中短暂停顿和识别器强制切段都能合并。持续静音不发消息，重复或迟到的识别回调不会导致重发。
- 助手回复期间说下一句，收音完整，宿主可接收时依序发送。用户同时编辑的文字草稿完整保留。
- 结束时验证尾句恰好发送一次、麦克风释放。切换聊天后，旧回调不能触发新聊天的发送。
- 三端分别验证权限拒绝、设备断开与转写失败的可见反馈。记录从用户实际说完到消息发出的耗时，并用真实对话检查误截断和等待过久的情况。

三端后端与自动投递均待运行验证。先在 DSH 面板验证完整两轮，再用同一组对话样本验证桌面适配器。

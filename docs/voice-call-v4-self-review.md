# 通话 v4 / 技术 v3 自审

日期：2026-11-15。范围是用户最新三项要求及“锄地仅为长任务例子”的补充。审查基于当前源码、安装 DSH 的本地实现与产品行为，不把新设计当作已完成实现。

## 第一遍：按用户场景推演

| 场景 | 发现 | 设计处理 |
| --- | --- | --- |
| 没打电话，只发文字 | 上一轮错误地创建只播报连接 | 撤回 DSH Send 的自动输出入口；新回归要求启动输出次数为 0 |
| 任务运行中再说话 | DSH queue 与核心 turnEnded 双重等待 | 统一 interject/steer，接收临界区不等待任务或整轮结束 |
| 改成 steer 但工具仍阻塞 | 本机 DSH 仅 next-step 插入，不抢占当前 step | 通用后台任务解耦；有版本核对的安全前台中断 |
| 用户闲聊与叫停 | 所有插入都取消业务会误停工作 | 聊天、停止声音、前台取消、业务取消四个范围分开 |
| 先答应去做，随后任务执行 | 旧适配器和核心都等待 turn/end 才播报 | 已提交消息片段独立于业务 turn 和任务终态 |
| 扬声器说话时用户插话 | 旧 gate 丢弃 VAD 输入，用户开口不可见 | 持续近端检测、回声处理、本地立即停播与预录 |

## 第二遍：竞态与抽象边界

发现并已补入方案：

1. 同 turn 可以消费多条 steer，不能用 turnId 或最新接收输入粗略归属回复；按 step 的已消费输入水位标注片段。
2. 客户端延迟 cancel 可能杀掉已经开始的新回答；新增 Host 原子核对 expected foreground 的要求，现有不带版本的 cancel 不能直接充当它。
3. unknown 接收不能成为所有后续闲聊的永久总锁；保留原身份且不重发，任务副作用使用自己的版本与回执。
4. “停下”之后旧异步任务启动请求可能迟到；外部执行前核对资源/任务意图版本，旧版本不能复活。
5. 后台通知可能混入同一 turn；采用片段来源与所属对话核对，不能整轮禁播，也不能开放外部社交来源。
6. 结束通话不能偷偷取消业务；重置也不能把旧任务无身份地迁入新会话。
7. 耳机测试不能代替 HECATE 扬声器双讲；请求 echoCancellation 不能代替实际回声与停播测量。
8. 已有 Jobs 并不自动托管任意 MCP；必须实现相应任务适配与生命周期，不只增加一段提示词。
9. DSH Jobs 默认“最终答复前收集作业”可能使模型再次长等待；新方案同时要求前台任务策略及工具路由调整，不能保留原长等待路径。
10. 配置仍拒绝 speaker-duplex，不能靠改枚举或伪装耳机宣称扬声器可打断；能力与校验迁移必须与实测一起完成。

以上是早先两遍自审的历史记录，不能据此判定方案没有缺口。随后独立审查发现下述 4 项；本轮按协议修订并继续复审。实际能力仍受宿主和工具限制，设计审查通过也不代表实现或设备验收通过。

## 第三遍：独立审查及修订

| 问题 | 触发与证据 | 修订 |
| --- | --- | --- |
| P1 接收 steer 后取消可能不再消费 | 当前 DSH 的 send/cancel/wakeDriver/kick 原方法最小探针：收尾后 idle、pendingInputs=1、restartedDrivers=0；探针 mock inbox/model，未操作真实通话 | 技术 §4 增加幂等中断身份、取消前收尾观察、可靠无正文唤醒、接管回执和未知结果核对；要求先证明当前宿主能力 |
| P2 任务归属混入临时绑定 | 当前 ConversationRef 含 runtimeId/bindingRevision，重载后失效 | 技术 §5 使用持久化 ConversationOwner，临时连接重新解析与鉴权；旧任务管理不依赖通话租约，不自动跨会话播报 |
| P2 启动回执丢失可能重复执行 | 外部执行成功与回执落盘存在崩溃窗口 | 技术 §5 增加派发前操作账本、operationId 唯一约束、原身份查询；非幂等外部接口结果未知时禁止自动重放；未知资源不随租约到期放行 |
| P2 打断后缺少 ASR 待决门禁 | 用户仍讲话或识别待决时旧响应可以新增片段；ASR 无 final 可无限等待 | 技术 §6–7 增加多 attempt 门禁、永久抑制被打断响应、收尾期限、失败恢复及旧回调隔离；不自动续旧句 |

同步收紧产品验收：停播 300 ms 从真实近端起音计时，包含检测延迟；每条设备路径至少 100 次真实插话尝试，漏检计失败，回放无人声场景同时检查误停播。不是本轮实测结果。

主审继续推演补充：目标输入在 DSH preStep 已 claim、step/start 尚未出现时也不得抢占；输入尝试与提交 unknown 分离，后者不持有 ASR 输出门禁。单按钮模式对已确定未提交的失败识别释放音频，不要求不存在的 held 管理面板；真正的设备/预算故障结束通话并恢复按钮关闭，保留在途提交核对与后台任务。

## 第四遍：修订后的独立复审

独立审查者重新阅读修订后的三份文档并核对核心预算/状态实现，确认一个新增 P2：ASR 失败保持 held 会耗尽 8 个输入名额，单按钮流程没有清理入口。已按上述“确定未提交则结算释放”规则修订，审查者复查后报告无未解决的高置信设计缺口。

主审同步核对以下交叉场景的设计收尾，结果是协议已有明确处理规则，不代表执行测试通过：

| 场景 | 最终处理 |
| --- | --- |
| 新输入已接收，旧 driver 被取消 | 取消前装收尾观察，原输入不重发，收尾后可靠唤醒 |
| 新输入已 claim，但尚无 step/start | 视为已接管，条件中断返回 stale，不误取消新输入 |
| 条件中断回执超时 | 按 interruptionId 核对，不再次无条件取消 |
| 任务启动回执丢失或派发时崩溃 | 按 operationId 查账，外部事实未知则不重放 |
| 停止结果未知，执行租约过期 | 撤销旧调度权，保留冲突资源隔离，不擅自交接 |
| Session reset / Host 重启 | 旧任务稳定归属不变，重新鉴权管理，不向新会话自动播报 |
| 用户说话时旧模型追加片段或任务完成 | 采集/识别门禁持续关闭输出，任务事实继续入账 |
| ASR 失败或超时，随后重说 | 从未提交的失败项释放音频和名额，新句继续，旧结果不晚发 |
| 转写成功，提交结果 unknown | 释放 ASR 门禁，原输入核对、不重发，不谎称未发送 |
| 多次起音、旧识别回调乱序 | 每个 attempt 单独收尾，不能解除其他 attempt 门禁 |
| 设备断开或真实预算耗尽 | 结束通话、按钮关闭并说明原因；任务继续，在途输入仍核对 |

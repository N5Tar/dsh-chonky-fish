# 大肥鱼资料导入 / 导出技术方案 V1

- 日期：2026-11-11
- 状态：V1 实现中；技术契约与实际代码差异以当前实现及测试为准
- 对应需求：[资料迁移方案 V1](<data-migration-design-v1.md>)
- 范围：身份与人格、钱包与账本、日记、活动技能库、通用偏好

## 1. 核心决策

1. 归属插件自身的「资料迁移」模块，模块名 `migration`，不是 DSH 宿主备份能力。
2. 用户入口为大肥鱼侧栏新增「设置」页，页内放「资料导入 / 导出」；不新增独立「迁移」一级菜单。
3. 只提供整包导出、预检、确认替换和结果反馈；不做合并、云同步或 Agent 工具。
4. 使用 `.fishpack` ZIP 文件；数据结构与业务文件解耦，不直接打包 home。
5. 保留现有存储布局；通过白名单投影与模块适配恢复数据，不做全量存储重构。
6. 导入前备份、暂存、短时维护，失败回滚；首次实现必须覆盖中途退出恢复。

### 3.1 建议文件结构

以下均为拟新增结构，不是已存在的实现：

```text
core/modules/migration/
  core.js                 # prepareExport / inspect / commit / status
  schema.js               # 存档与业务投影的严格结构校验
  policy.js               # 唯一字段白名单、安全覆盖规则
  errors.js               # 稳定错误码
  tests/                  # 核心、故障注入、HTTP、客户端测试

app/shared/storage/migration/
  archive.js              # 有界 ZIP 读写、路径与摘要校验
  repository.js           # 五类资料读取、构建目标文件
  transaction.js          # 暂存、备份、提交日志、回滚与启动恢复

app/shared/storage/
  migration-gate.js       # 插件内相关读写共用的维护门禁

app/dsh/adapters/migration/
  index.js                # installMigration，ready / close 生命周期
  http.js                 # 路由、流式上传下载、错误映射

```

### 3.2 职责约束

- `core` 不 import DSH、文件系统、ZIP 库或 DOM，通过注入端口编排。
- 文件系统层不决定哪些配置可以迁移，白名单只定义在 `policy.js`。
- Host 负责安装与注入，不继续往入口文件堆积打包和事务代码。
- 现有日记、技能模块继续拥有自身业务校验；必要时提取可复用验证函数，不复制第二套规则。
- 迁移不注册 `fish_migration` 等模型工具；仅主人界面操作，不允许技能正文触发恢复。
- ZIP 使用跨平台 Node 库，不调用系统 `zip` / `unzip`。建议评估 `yauzl` / `yazl`；实现前确认版本、许可证与安全维护情况，再固定依赖和锁文件。

## 4. 数据模型与恢复映射

### 4.1 包内结构

```text
manifest.json
identity.json
wallet.json
preferences.json
profile/<相对路径>
diaries/YYYY-MM-DD.md
skills/<skillId>.json
```

`manifest` 必需字段：`format: 'chonkyfish-fishpack'`、`version: 1`、`createdAt`、`pluginVersion`、`sections`、`files`、`warnings`。

- `sections` 必须声明五类内容及计数，空目录无需 ZIP 目录条目，使用计数和文件清单表达。
- `files` 记录除 manifest 自身以外的每个载荷文件：`path`、`bytes`、`sha256`。未列出的条目、重复条目或缺失条目均拒绝。
- 包内 JSON 使用 UTF-8；正文文件保持原始字节。不得通过重新排版正文改变内容。
- 拒绝不支持的格式版本；V1 不承诺自动兼容未来版本。

### 4.2 字段映射

| 包内内容 | 来源 / 恢复位置 | 规则 |
|---|---|---|
| identity | 状态中的 `name`、`prompt` | 不导出 `messages`、`savedAt`、旧资料路径；恢复时合并到目标状态 |
| profile | 默认个人资料目录 | 仅普通文件；显式排除顶层 `browser-profile` 运行目录；恢复后 `profileDirectory` 设置为目标默认目录 |
| wallet | 状态中的 `balance`、`ledger` | 整体替换；不按账本反推余额，不生成新交易 |
| diaries | 日记目录 | 合法日期与正文；校验全部条目，不依赖日常 list 的条数限制 |
| skills | 技能目录 | 完整存档；复用技能导入验证，但不走拒绝同 ID 的逐项导入发布逻辑 |
| preferences | 通用配置白名单 | 以目标配置为基底，仅替换迁移字段及明确的安全覆盖字段 |

身份与钱包恢复时构造一份新的目标状态文件，一次发布，避免同一文件被两个步骤相互覆盖。账本条目保留 `id`、`title`、`amount`、`date`，验证数值有限、类型合法及条目 ID 不冲突，不凭日期展示字符串推测真实时间。

### 4.3 V1 偏好白名单

| 分组 | 纳入字段 |
|---|---|
| 日记 | `diary.enabled`、`diary.maxContentChars` |
| 技能 | `skills.enabled` |
| 事件引擎 | `eventEngine.enabled`、`extractTickMs`、`extractBatch`、`maxRecordsPerTurn` |
| 感知 | `perception.enabled`、`rawTtlMs`、`summaryTtlMs` |
| ABS | `timeScale`、`restHours`、`reviewIntervalMinutes`、`reviewMinRealGapMinutes`、`activationCooldownMinutes`、`feedback`、`drives` 中当前支持的显式叶子字段 |

安全处理：

- 不导出 `abs.mode` 和 `proactive.enabled`；导入时分别设置 `shadow` 和 `false`，阻止迁移隐式启动主动投递。
- 感知模块可用性 `perception.enabled` 不等于采集授权。目标采集选择设为关闭，并停止当前采集器；不迁移活动数据库。
- 不导出 `policyVersion`；由目标插件提供。配置中的历史运行状态不纳入。
- 感知采集选择文件的修改属于安全覆盖例外，要纳入同一备份与回滚计划。
- 其他配置字段保留目标值；新增字段必须显式加入白名单才能进入包。
- 导出从读到的原始配置投影偏好：仅缺失的旧版白名单字段采用明确默认值；已出现但类型/范围非法的字段拒绝导出，不用运行时消毒器静默替换为默认值。
- 日记、技能等载荷限额必须同时满足目标版本支持的限制和包内偏好，不能恢复后变成不可读取的数据。

## 5. 功能与接口

统一前缀 `/chonkyfish/migration`；路径与限额登记到资源规格。上传采用原始二进制流，不使用 Base64 JSON。

| 方法与路径 | 功能 | 结果 |
|---|---|---|
| `GET /status` | 查询维护状态；`GET /imports/commit?id=<importId>` 查询单次操作 | 轻量 JSON，不返回正文或秘密 |
| `POST /exports` | 取得一致快照，准备导出 | `exportId`、摘要、体积、警告、有效期 |
| `GET /exports?id=<exportId>` | 下载已准备的包 | ZIP 字节流、附件下载头 |
| `POST /imports/inspect` | 上传包、完整校验并暂存 | `importId`、包摘要、目标资料版本、安全提示、有效期 |
| `POST /imports/commit`，JSON `{ "id": "<importId>" }` | 确认整份替换 | 接纳后返回操作 ID，通过操作状态查询结果 |
| `POST /imports/cancel`，JSON `{ "id": "<importId>" }` | 取消尚未提交的预检 | 删除暂存；提交过程中拒绝取消 |

接口约定：

- JSON 使用 `{ok:true,data:...}` / `{ok:false,error:{code:...}}`，错误不回传正文或内部堆栈。
- commit 只接受服务端已预检的 ID 和目标版本，不接受客户端传入目标路径或恢复文件列表。
- 预检 ID 与当前管理上下文绑定，10 分钟过期；不因持有 ID 就跳过请求保护。
- 提交接纳后即使页面关闭，Host 继续完成或回滚；断网后查询状态，不自动创建第二笔导入。
- 同一 `importId` 重复 commit 返回同一结果；同一个包重新上传可以再次替换，但不会增加历史。
- 导出快照与预检文件到期清理；提交和恢复中的文件不得被清理器删除。
- 接口不提供任意本机路径读取、上传后自动执行或模型调用。

主要错误码：`INVALID_ARCHIVE`、`UNSUPPORTED_VERSION`、`LIMIT_EXCEEDED`、`UNSAFE_PATH`、`INVALID_DATA`、`MIGRATION_BUSY`、`STALE_TARGET`、`BACKUP_FAILED`、`IMPORT_FAILED`、`RECOVERY_REQUIRED`。

V1 建议硬上限：压缩包 128 MiB、总解压 256 MiB、载荷文件 10000 个、普通单文件 16 MiB、压缩比 200:1。manifest 最大 4 MiB；技能继续遵守现有 512 KiB / 技能等限制，其他业务限额继续生效。超限整包拒绝，不截断；这些值集中定义、测试验证，不允许从包内放宽。

## 6. 一致性、事务与生命周期

### 6.1 维护门禁

资源层提供共享读写门禁：状态、配置写入、日记、技能和本地采集偏好通过短租约保护；写入在维护期拒绝，门禁内读取等待独占操作完成。门禁不替代各自存储的串行化：

1. HTTP / 工具普通读写先取得资源层租约，再进入各自写入队列或读取流程。
2. 同步运行态配置读取在维护期使用迁移前的稳定配置快照；系统提示人格读取使用缓存，维护期间不读替换中的 state，释放后强制刷新。技能与采集能力在维护期不可用。
3. 导出、预检、确认申请独占维护；拒绝新写入，等待已接纳资源访问结束。
4. 导出 / 预检锁内复制一致快照并双重核对目标指纹；压缩在锁外。预检记录指纹，用户确认期间不持锁。
5. 导入锁内复核目标指纹、备份、替换并做恢复；HTTP 资料路由返回 `MIGRATION_BUSY`；维护结束或回滚后释放，避免观察到半新半旧资料。

门禁覆盖插件 HTTP 和模型工具服务，不只覆盖按钮。个人资料目录没有统一插件写入 API，通用 bash / write / edit 和外部编辑器不能被此 gate 自动拦截；V1 仍依赖双重目标指纹和确认前复核来发现此类修改，不能声称具备跨进程文件锁保证。

### 6.2 防止旧界面回写

当前面板会延时保存整份状态，仅在服务端加锁不足以避免导入后的旧缓存覆盖。

- 新增服务端资料 generation；导入、正常资料修改均使对应目标版本失效。generation 保存在迁移元数据，启动时加载，不能每次重启归零。
- 状态读取返回 generation，保存必须携带；缺失或过期返回 `409 STALE_TARGET`，前端先重新读取，不自动重试旧 body。
- 配置修改采用同等版本检查，日记和技能保留自身并发规则，并参与 gate 和目标版本更新。
- 预检记录目标版本；确认时资料已变化则重新预检，不悄悄覆盖确认期间新增的交易或日记。
- 导入完成发送页面内刷新通知；其他标签页即使未收到通知，也由服务端版本检查阻止回写。
- 先升级现有面板保存协议，再开放导入入口，避免新旧代码混用。

### 6.3 本地事务

拟新增私有目录，路径由资源管理器解析：

```text
$DSH_HOME/chonkyfish/migration/
  exports/<id>.fishpack
  staging/<id>/
  transactions/<id>/
    stage/<target-index>
    backup/<target-index>
    transaction.json
```

不改现有日记、技能和个人资料的正式位置，不将 migration 目录包含在导出中。提交事务目录保留 `committed` 状态的旧数据备份；失败回滚的数据不再作为备份保留。

实际提交状态顺序：

1. 锁内检查预检时的目标指纹，并记录每个目标原先是否存在以及个人资料目录中要保留的 `browser-profile`。
2. 先原子写入并刷盘 `prepared` 日志，再构造新目标文件；文件内容刷盘、目录同步后，写入 `staged`。
3. 写入并刷盘 `publishing` 后逐项把旧目标改名到 backup、把新目标从 stage 发布；每次 rename 后同步相关目录。浏览器运行资料从旧目录原样移动到新目录，不从包导入。
4. 全部发布后更新运行态 generation，再原子写入并刷盘 `committed`；只有此后才报告提交成功。
5. 启动恢复：`prepared` / `staged` 没有改动正式目标，清理事务；`publishing` 按备份回滚；`committed` 保留新资料和备份。事务目录非空但缺少日志，或日志路径/内容不可信时，失败关闭为 `RECOVERY_REQUIRED`，不能静默继续。

失败时按持久化备份恢复全部涉及对象。回滚失败或提交标记持久化状态不确定时进入 `RECOVERY_REQUIRED`，不清理可能仍需恢复的备份。

事务日志通过同目录临时文件、文件 fsync、原子 rename 和目录同步更新；stage 文件也先刷盘，正式目标的 rename 同步源/目标目录。POSIX 使用现有目录 fsync 能力；Windows 目录同步实现为空，因此不声称各平台/文件系统具有相同的断电持久性。

### 6.4 启动与重载

- 将迁移恢复检查放在 layout 准备完成之后、状态/配置可写路由和日记/技能/ABS 等消费者 ready 之前。
- 未完成事务在开放模块前回滚；若恢复失败，阻断相关模块 ready，但允许设置页显示恢复错误。
- 导入提交不创建会话、不触发日记或技能执行，也不改社交与定时任务。
- ABS 运行记录不替换；配置变化通过既有服务边界应用，不能靠改磁盘使内存仍处于 active。
- 日记 enabled 等启动时配置，在未提供可靠热重载时返回 `restartRequired: true`。安全关闭必须立即生效，不能等重启才停止主动投递。
- 插件关闭时拒绝新操作；已开始事务留足恢复信息，避免清理钩子误删备份。

- 沿用模块页样式、主题变量和中英文文案；不建设新的设计系统。
- 文件选择接受 `.fishpack`，服务端仍按内容严格校验；UI 使用可访问确认组件而非浏览器 confirm。
- 打开设置页不创建聊天会话，不调用模型。

## 8. 请求保护与隐私

现有项目多数接口不设插件私有 token，不能据此推断宿主一定保护新路由。

- 迁移路由必须调用 DSH Connection 的 `requestRejection(request)` 复用 Host 的认证与 loopback / Origin 信任检查；拒绝时按 Connection 给出的 401 / 403 终止。
- DSH Desktop 的 `dsh-app://app` 请求由 Electron 主进程转发到 Host，并附带 Host 签发的浏览器会话 Cookie；转发会移除 `Origin` 与 `Sec-Fetch-Site`。因此不能只靠这两个请求头识别 Desktop，也不能为桌面自定义源宽泛放开 CORS。
- 导出准备、下载、预检、确认、取消与状态查询全部验证同一 Host 管理会话；不因 GET 或知道 ID 就开放隐私读取。
- 成功/失败日志只记录操作 ID、阶段和错误码，不记录正文、整个账本或包内容。
- 直接未认证的 loopback `curl` 应得到 401；它不是桌面界面端到端验收。桌面验收应确认 IPC 转发请求携带有效 Host Cookie 并由 Connection 接纳。
- V1 不提供包加密；界面明确说明资料包包含隐私，应由用户安全保存。

## 9. 实施顺序与验收

| 阶段 | 交付 | 完成条件 |
|---|---|---|
| 1. 数据契约 | 白名单、严格 schema、投影与包格式 | 五类往返测试、空集合和限额测试通过 |
| 2. 存储与安全边界 | ZIP、gate、generation、暂存与事务恢复 | 并发写入、旧缓存、逐步失败与重启恢复测试通过 |
| 3. 宿主接线 | 模块安装、接口、ready、重载 | HTTP 和工具写路径都受门禁；范围外数据不变 |
| 4. 设置页面 | 菜单、上传预检、确认、下载、结果 | 中英文、忙态、失败态、取消、关闭后继续查询通过 |
| 5. 集成验收 | 构建与真实安装验证 | 不同 home、macOS / Windows、已有资料覆盖与回滚验证 |

拟增加 `test:migration`，并接入总测试；回归现有人格、日记、技能、资源、ABS 和感知测试。文档阶段不运行功能验收，不把测试计划当作已通过证据。

关键验收：钱包不翻倍、技能不追加版本、日记不截断、外部路径不跟随、旧面板不回写、自动行为不开启、故障可恢复、范围外数据不修改（明确的安全关闭例外除外）。

完成实现后通过现有客户端构建生成产物，Host 代码更新需要重启宿主，客户端刷新后验证原有 GUI；不启动替代服务器作为验收。

## 10. 范围控制

本方案只增加一个管理模块和一个设置入口，不扩展为 DSH 备份框架。完整环境迁移、会话与附件恢复、同步、加密保险库、智能合并、备份管理中心和模型迁移工具均不属于 V1。

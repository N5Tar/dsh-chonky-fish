# 大肥鱼架构调整设计 v1

- 日期：2026-11-11
- 状态：方向已确认，实施前设计；本文不表示重构已完成。
- 本次性质：整理和解耦现有实现，不新增业务能力、不实现桌面应用。

## 1. 已确认的设计决策

1. 未来产品形态包含 DSH 插件版、macOS 桌面版和 Windows 桌面版。
2. 核心业务模块归入 `core/`，应用入口归入 `app/`。
3. 三个 APP 分别拥有自己的 UI，不共享页面、组件、样式或带交互逻辑的 ViewModel。
4. 立绘、头像、动画帧等现有素材共享，各 APP 决定如何使用和呈现。
5. 本次只调整已有代码的架构、文件布局和依赖关系。现在有什么就保留什么，不为未来平台补齐能力。
6. 当前没有 macOS 或 Windows 桌面 APP。`app/macos/`、`app/windows/` 只作为未来应用位置记录在设计中，本次不创建空应用、空入口或占位实现。
7. 已有 Windows 文件系统兼容代码不等于 Windows APP；已有 macOS 原生采集组件也不等于 macOS APP。它们归公共平台适配层，继续供 DSH 插件使用。
8. 采用渐进式重构，现有 DSH 插件是本次唯一必须保持可运行的应用交付形态。

**总体方向：共享核心能力、非 UI 技术实现和素材；应用界面各自拥有。业务不分叉，界面不强求一致。**

## 2. 范围与非目标

### 2.1 本次范围

- 盘点现有模块、宿主依赖、平台代码、数据与构建资源。
- 拆分业务规则、用例编排、外部能力接口和具体适配实现。
- 将 DSH 插件的 Host、Client、预设、路由和发布配置归入明确的应用边界。
- 保留 DSH 自有 UI，调整源码归属与依赖，不重新设计页面。
- 整理已有共享素材、平台兼容逻辑和 macOS 原生采集实现。
- 调整构建、测试、打包、资源寻址和文档，确保迁移后仍可交付现有插件。
- 建立必要的依赖检查与适配契约回归测试。

### 2.2 明确不做

- 不新增业务模块或修改业务规则。
- 不实现 macOS / Windows 桌面窗口、托盘、通知、安装器或自动更新。
- 不新增 Windows 活动采集等原生能力。
- 不新增模型提供方、Agent 引擎或替换 DSH 运行时。
- 不因架构调整锁定 Electron、Tauri 或原生 UI 技术。
- 不建设共享 UI 库、跨端页面框架或统一前端状态层。
- 不迁移用户数据根目录、不统一所有存储格式、不合并现有数据库。
- 不建设云同步、微服务、插件市场或通用插件框架。
- 不默认进行全量 TypeScript 改写或更换测试框架。
- 不创建没有当前调用者的接口、空平台包或伪造的能力实现。

原方案中的“桌面纵向原型”“补齐 Windows 能力”“桌面签名、安装和更新”等工作，均移出本次计划。

## 4. 两个独立维度：运行宿主与操作系统

- 运行宿主：当前为 DSH；未来可能增加独立桌面运行时。
- 操作系统：现有代码包含 POSIX / Win32 兼容实现及 macOS 原生采集。

DSH 插件本身可能运行在不同操作系统上，所以平台实现不能归属于某个桌面应用入口，也不能要求先启动桌面壳才能使用。

本次仅整理已有组合，不将“存在适配代码”描述成“完整支持该平台”或“已经实机验证”。例如 Windows 路径测试通过，不代表 Windows 活动采集存在。

### 5.3 包与发布边界

- 目录边界不等于 npm 包边界，初期保留单仓库与现有发布入口即可。
- 不要求每个模块创建独立包，也不把 workspace 改造作为前置条件。
- 根清单、插件导出或构建入口可在过渡期保留为兼容入口，内部转向新目录。
- 将配置归入应用边界时，必须同步处理发布清单和引用关系；不能只移动文件。
- 生成产物仍由构建生成，不能手改产物代替源码迁移。

## 6. 依赖规则

### 6.1 核心与适配器

```text
app/dsh 的装配入口
    ├── 使用 core 的业务用例
    ├── 创建 app/dsh/adapters 的宿主适配器
    └── 创建 app/shared 的存储、渠道和平台适配器
                 │
                 └── 按 core 的接口提供具体能力
```

- `core/` 不导入 `app/`，也不直接接收 DSH `ctx`、Agent 实例、HTTP 请求或 UI 对象。
- 核心通过注入的能力完成持久化、会话投递、模型调用等副作用。
- 文件系统、SQLite、网络连接、子进程与操作系统选路由具体适配器负责。
- 核心不能只是包裹 DSH API 的薄转发层；接口按现有业务需求定义。
- 纯计算逻辑不引入宿主或操作系统分支；现有时间、ID 等依赖按测试和迁移需要注入，不为抽象而逐项造框架。
- `app/shared/` 不导入具体应用入口，不包含 DSH 生命周期或 preset 假设。
- 跨业务模块通过明确导出的用例或契约协作，避免直接操作对方存储。

### 6.2 UI 所有权

- DSH UI 归 `app/dsh/ui/`；未来 macOS / Windows UI 分别归各自 APP。
- 不在 `app/shared/` 或 `core/` 放共享页面、组件、CSS、前端 hooks、导航或带交互逻辑的 ViewModel。
- 核心提供业务操作和状态，不提供“打开弹窗”“切换侧栏”或某 APP 专用卡片布局。
- UI 不能绕过后台业务用例直接读写数据库或启动采集进程。
- 可以共享业务契约与素材清单，但不要借此共享页面状态机。
- 本次不要求把现有页面重写为另一种组件体系；保留 DSH 页面外观和行为。

### 6.3 接口抽取尺度

只按现有调用链抽取必要接口，候选边界包括：

| 边界 | 当前用途 | 限制 |
|---|---|---|
| 会话与消息投递 | 现有聊天、社交、主动消息、自省 | 不实现新的 Agent 引擎，不复制整个 DSH API |
| 会话历史与持久化确认 | 事件提取、投递确认、恢复 | 保留原有顺序、来源和确认语义 |
| 模型调用 | 现有事件提取 | 不新增模型配置体系 |
| 存储仓储 | 各模块读写和版本校验 | 保持当前格式、事务和并发语义 |
| 时间与调度 | 已有 ABS 时间模型和后台任务 | 不增加新的自动任务 |
| 感知 | 现有采集启停、样本处理、能力状态 | 不新增 Windows 采集 |
| 渠道 | 现有连接、收发与重试 | 不改变绑定、回复范围和投递行为 |

优先沿用已有注入点。单个模块使用的接口可以留在模块内部，只有确实跨模块使用时才提升到公共目录。

## 8. 必须保持的行为与数据契约

### 8.1 能力基线

迁移前记录并在迁移后回归：

- 聊天、人格配置、现有工具接入、会话绑定与历史读取。
- 事件引擎采集、提取、查询、消费、重试和去重。
- ABS 状态、时间模型、自省和客观反馈。
- 主动消息的现有触发与投递方式。
- 日记读写、技能库修订与历史、零花钱和账本状态。
- 社交渠道连接、主人绑定、访客独立会话、自动回复和恢复。
- 现有感知采集范围、隐私边界、启停行为及不支持状态。
- DSH 页面、头像、素材、配置和诊断展示。

上述清单是现有行为的回归范围，不是要求增加其中尚不存在的扩展功能。

### 8.2 不能简化掉的语义

- 已接收、已持久化、已执行完成、已发往渠道不能合并成一个成功标记。
- 保留事件序号、来源、身份、游标、租约、幂等键和版本校验等现有约束。
- 保留已取消的渠道工具限制这一现状；不借重构重新增加来源门禁，也不额外扩大权限。
- 保留当前宿主权限行为、主人绑定、访客会话隔离和回复路由，不重新定义安全策略。
- 模块卸载、重载、退出时仍正确释放定时器、订阅、数据库、网络连接和子进程。
- 后台能力不迁到页面生命周期中，不因页面挂载导致重复启动。
- 继续明确不支持、未知、失败和投递不确定等状态，不以空实现伪装支持。

### 8.3 数据与配置

- 继续使用现有 DSH 数据根目录、文件布局、schema、配置默认值和版本规则。
- 数据根目录由 DSH 适配层解析，再传给业务与存储装配；核心不直接读取 `DSH_HOME`。
- 代码搬迁不等于用户数据迁移，不自动移动或重建用户目录。
- DSH 会话日志继续由 DSH 管理，不复制进插件业务库作为新权威来源。
- 保持工具名称、参数、返回结构和路由兼容；若实现中发现必须破坏兼容，应单独提出决策，不能混入本次重构。

## 9. 实施阶段与验收关卡

### P0：盘点与基线

工作：记录模块清单、文件映射、依赖、数据位置、对外契约、当前测试及已知问题。

验收：明确哪些能力已有、哪些平台未实现、哪些测试只在模拟环境执行；不得将既有问题包装为本次新增任务。

### P1：建立边界并迁移低耦合模块

工作：优先整理日记、技能、人格等模块，将业务规则与宿主注册、存储分开；保留必要兼容入口。

验收：相关现有测试通过；提取后的业务测试不需要加载 DSH；当前插件仍能加载。

### P2：迁移复杂业务与适配层

工作：整理事件引擎、ABS、主动消息、社交、感知；区分业务语义、DSH 事件映射和平台实现。

验收：投递确认、幂等、恢复、生命周期和既有能力状态保持不变；不新增原生平台支持。

### P3：整理 DSH UI、素材与构建

工作：将现有 UI 和宿主桥接归入 DSH 应用，整理素材及原生资源引用，更新打包清单和测试路径。

验收：页面外观和交互保持不变；构建产物、插件导出、预设及素材加载正常；原生组件仍可由 DSH 找到和启动。

### P4：整体回归与文档收口

工作：执行现有全量测试、依赖检查、构建和实际插件加载验证；同步模块说明与平台文档。

验收：满足第 10 节。没有桌面应用原型、Windows 能力补齐或安装更新阶段。

各阶段允许小步交错，但不要让一次提交同时包含全量移动、业务改写、UI 重做和数据格式变更。

## 11. 风险及控制

| 风险 | 控制方式 |
|---|---|
| 只搬文件，核心仍然依赖 DSH | 检查导入图和注入参数，核心测试不加载 DSH |
| 为假想桌面能力过度抽象 | 每个接口对应当前调用者，不创建空实现 |
| 改路径导致发布遗漏 | 核对 package 导出、files 清单、构建注入、原生二进制与 schema 资源 |
| 抽象层丢失持久化或事件语义 | 使用现有案例做适配契约测试，重点覆盖不确定状态和重启恢复 |
| 重构时顺便改变权限或业务行为 | 对照基线审查，行为修改单独讨论和提交 |
| 核心迁移带来数据目录变化 | 显式注入原路径，保持用户数据布局不动 |
| 平台代码被误认为桌面应用 | 平台实现留在公共适配层，桌面 APP 目录仅写未来规划 |
| 大规模搬迁难以回滚 | 按模块提交，必要时保留薄兼容入口，不产生新数据格式依赖 |

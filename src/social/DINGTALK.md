# 钉钉企业应用机器人 · Stream

## 配置

1. 在钉钉开发后台创建企业内部应用，启用机器人能力，选择 Stream 模式并发布；应用可见范围应包含使用者。
2. 在小鱼塘 **社交 → 钉钉 → 新增连接** 填写连接标识、Client ID、Robot Code、Client Secret。两个 ID 按后台实际值分别填写。
3. Secret 直接保存为本机值，不依赖环境变量。配置为本地明文（POSIX 0600），不是加密保险库；编辑留空保留原值，改变连接/应用身份必须重新填写。管理响应只返回是否保存，不回传 Secret。
4. 修改 Host 插件代码后完整重启 Harness；仅刷新页面不会重载 Host 模块。

[官方接收消息说明](https://open.dingtalk.com/document/robots/receive-message.md)；[Stream 协议](https://open-dingtalk.github.io/developerpedia/docs/learn/stream/protocol/)。订阅主题 `/v1.0/im/bot/messages/get`，不需要公网 HTTP 回调或 OneBot。

## 用绑定码认领主人

1. 连接显示已连接后，点 **生成绑定码**。
2. 复制完整绑定码，在钉钉**私聊机器人**发送；不要转发或发送到群。
3. 绑定码 10 分钟有效、只能使用一次。新生成的码替换旧码；已绑定主人在新码被成功使用之前不变。
4. 配对控制消息不会进入模型上下文；无效、过期、群聊中的配对码也不会成为普通聊天输入。限流保护限制猜测。
5. 面板显示已绑定后，主人正常私聊即可进入当前大肥鱼主会话。改绑使用 **生成改绑码**。

不会把“第一个私聊的人”“最近私聊的人”或昵称自动当成主人。后台使用连接、应用身份版本和发送者 ID（存在时含企业 ID）识别。绑定码由本机用户操作生成，不提供给模型授权工具。

## 会话和回复

- **DSH 输入**：只在 DSH 回显，不向钉钉广播。
- **绑定主人的私聊**：原文进入当前小鱼塘主会话。新开主会话后，新消息跟随新会话；已有 turn 的返回目标不变。
- **其他发送者**：自动创建并绑定独立会话，之后同一发送者私聊沿用它，不混入主人主会话。
- **群聊 @**：按发送者和群隔离会话，即使发送者是主人也不加载主人私聊历史。避免群聊请求把主人的私密上下文带回群。
- 会话忙时入站排队，不把外部消息插入正在运行的 turn。每条消息逐轮处理。可能产生模型调用费用。
- 模型只收到普通 user 正文，没有 JSON/notice/发送者/渠道前缀。Host 为该 turn 登记附加返回目标，最终文本既保留在 DSH 对应会话，也投递原渠道。
- 不发送 reasoning、工具输出、中断回复；最后一条 assistant 消息必须是最终纯文本。若用户在运行中追加 DSH 输入导致混合来源，不外发该轮，面板给出诊断；不能靠“只发送 assistant 文本”保证混排隐私。
- 访客使用独立预设和工作区，提供网页、文件、命令等通用工具；不加载主人补充资料、不共享主人会话历史。工作区分离不是文件系统沙箱，工具仍遵守会话实际的 DSH 权限。
- 社交模块不安装按渠道来源禁用工具的 guard；主人、访客、群聊轮次都可以使用各自会话已有的工具。来源标记仅用于回复路由与会话隔离，不作为工具禁用条件。

## 主动消息与能力说明

钉钉连接正常时，人格后的 **能力说明** 动态加入钉钉一项：已经绑定主人时，告诉大肥鱼可以通过钉钉主动找到主人、分享近况和聊天；未配对则明确提示尚不能联系主人。断线或插件关闭后移除。能力说明只描述可用能力，不标记当前消息来源，也不披露账号或凭证。

工具 `social_send_owner_message` 在大肥鱼主会话可用（包括来自钉钉的主人私聊轮次），输入 `operationId` 与 `text`（最多8000字符），不能指定任意联系人。

目标必须是**已配对主人**，陌生人后来发消息不会改变它。有效 sessionWebhook 优先；过期后使用绑定的企业 staffId，通过企业应用 access token 与 `oToMessages/batchSend` 发送，需要相应钉钉权限。没有可用身份或地址时明确失败。默认主动发送间隔10秒。

## 持久化与恢复

- 新身份绑定、入站投递登记、turn 回复意图、发送幂等账本分别持久化。旧文件不删除、不盲目重放旧回复。
- 访客 sessionId 先持久化预留再创建，失败恢复沿用同一 ID，不重新分配另一会话。
- 回复使用实时已提交事件，不再扫描完整日志推断归属。已完成且确认未发送的意图可以恢复；发送中断后结果不明确为 unknown，不自动重试。
- Host 重启时未完成 turn 不保证补发；请看面板状态并发送新消息继续。
- 仅已知未开始发送的断连/限流可等待重试；失败与 unknown 不驱动盲目补发。
- 路由存储有容量上限（1024 路由）；达到上限明确拒绝，不静默淘汰仍可能防重的记录。
- 所有 webhook、token、配对码及身份映射是后台数据，不进入模型正文。私有文件备份也包含敏感数据，不应共享。

## 传输诊断和联调

0.4.9 使用支持控制帧的 `ws` 传输，开启主动 WebSocket Ping/Pong：连接打开后每轮等待8秒发送一个带随机标识的Ping，8秒内收到对应Pong即确认存活并安排下一轮；超时立即终止旧socket、重新取得网关ticket并重连。关闭插件会清理全部探测定时器，旧连接的延迟回调不能影响新连接。

这与 Stream 应用层的 `SYSTEM/ping` 不同：后者仍按协议立即回显opaque。也不再把“120秒没有聊天/应用层帧”当作断线。面板显示Ping/Pong计数、最近Pong、往返时间、超时次数和断线原因；“Pong已确认”只证明当前连接可往返，不保证平台已将每条消息推到此连接。

依据：[官方协议系统推送](https://open-dingtalk.github.io/developerpedia/docs/learn/stream/protocol/#系统推送)及[官方Node SDK keepAlive实现](https://github.com/open-dingtalk/dingtalk-stream-sdk-nodejs/blob/main/src/client.ts)。SDK的keepAlive默认false，8秒为其可选实现策略，不是协议规定的强制间隔。新增测试使用本机真实WebSocket服务器，验证无业务消息也可保活、丢Pong但TCP未断时自动恢复，以及恢复后继续收信；未使用真实钉钉凭证。

此前观察到周期性重连，但尚不能断言它就是所有后续消息丢失的唯一根因。单独建立一个同应用 Stream 探针可能参与平台分流，不应与生产连接竞争。

验证顺序：

1. 重启后连接并完成主人配对，打开主会话。
2. 主人连续发三条不同文本，确认每条都有 DSH 和钉钉回复。
3. 在 DSH 输入普通消息，确认钉钉没有收到该轮输出。
4. 换一个钉钉发送者，确认建立独立会话且主会话没有对方消息；再次发送仍在原独立会话。
5. 新开主人主会话，再从主人钉钉发送，确认进入新会话。
6. 空闲十分钟后再次发送，查看连接次数/帧计数定位断连和收信问题。

本地 mock 测试不等于真实钉钉收发验收；真实联调结果须另行记录。

## 限制与错误

仅支持文本；群里必须 @机器人。暂不支持附件、指定消息引用、任意联系人主动推送；普通自动回复 webhook 过期时不擅自改为另一个目标。发送超时或不明确响应一律 unknown，禁止换 operationId 重发。

- `SOCIAL_NO_OWNER_CHAT`：先生成绑定码完成主人配对。
- `SOCIAL_WEBHOOK_EXPIRED`：回复地址过期，需新消息刷新。
- `SOCIAL_REPLY_MIXED_TURN`：混合 DSH 输入，为避免外泄仅保留 DSH 输出。
- `SOCIAL_REPLY_STORAGE_UNCERTAIN`：回复存储不可确认，停止外发。
- `SOCIAL_CONNECT_FAILED`：检查应用发布、Client ID/Secret、网络和权限。
- `SOCIAL_EVENT_IDENTITY_MISMATCH`：回调 Robot Code 与配置不一致。
